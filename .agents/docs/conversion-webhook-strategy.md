# Conversion Webhook Strategy

> **Spec reference**: Section 0.17 of `terraform-removal-migration.md`
> **Related doc**: [crd-versioning-strategy.md](crd-versioning-strategy.md) (Section 0.8) — covers *which* versions are served; this doc covers *how to safely convert* between them without panics.

## Overview

This document covers the conversion webhook infrastructure as it relates to the TF→native migration:

1. Why the `zz_generated.conversion_spokes.go` pattern causes panics when native types are involved
2. Why the parallel phase (RAW types) is safe — no changes needed
3. How the global kustomize webhook patch interacts with native CRDs
4. Concrete remediation steps at cutover for affected services
5. A complete inventory of all files at risk

---

## The Problem: `resource.Terraformed` Type Assertion

Every API version package contains a generated file `zz_generated.conversion_spokes.go`. For
types that are **spokes** (i.e., an older version that converts *through* a newer hub version),
the file looks like this:

```go
// apis/cluster/rds/v1beta1/zz_generated.conversion_spokes.go
// Code generated by upjet. DO NOT EDIT.

import (
    ujconversion "github.com/crossplane/upjet/v2/pkg/controller/conversion"
    "github.com/crossplane/upjet/v2/pkg/resource"
    "sigs.k8s.io/controller-runtime/pkg/conversion"
)

func (tr *Instance) ConvertTo(dstRaw conversion.Hub) error {
    spokeVersion := tr.GetObjectKind().GroupVersionKind().Version
    hubVersion   := dstRaw.GetObjectKind().GroupVersionKind().Version
    if err := ujconversion.RoundTrip(dstRaw.(resource.Terraformed), tr); err != nil {  // ← PANIC HERE
        return errors.Wrapf(err, "cannot convert from the spoke version %q to the hub version %q", spokeVersion, hubVersion)
    }
    return nil
}
```

The line `dstRaw.(resource.Terraformed)` is a **type assertion**. It succeeds only if the
destination object implements the `resource.Terraformed` interface (which requires, among
other things, `GetTerraformResourceType()`, `GetParameters()`, `SetParameters()`, etc.).

**Native (RAW) types do NOT implement `resource.Terraformed`** — they are plain Crossplane
managed resources with no Terraform state. Therefore, if Kubernetes ever calls `ConvertTo` on
a spoke type and passes a native type as the hub, this assertion panics at runtime.

A panic in the conversion webhook handler causes:
- The conversion request to fail with a 500 Internal Server Error
- Kubernetes to refuse all `get`, `list`, `create`, `update`, `patch`, and `delete` operations
  on that resource kind (for ALL versions — not just the one being converted)
- Effectively **blocking all access** to the affected CRD

---

## Parallel Phase (RAW Types): No Changes Needed

**During the parallel phase, RAW types use a single API version.** The panic cannot occur.

Rationale:
- RAW types are scaffolded in `apis/cluster/<service>/v1beta1/native/` as a separate sub-package.
- They expose exactly one API version (e.g. `v1alpha1` or `v1beta1` in the `native/` sub-package).
- Kubernetes only calls the conversion webhook when a CRD **serves multiple versions**. A
  single-version CRD never triggers conversion, regardless of the webhook strategy in the CRD spec.
- The TF types and native RAW types are **distinct Kinds** (`Bucket` vs `BucketRAW`) with
  separate CRDs — they don't share a CRD and therefore don't share a conversion webhook.

**Conclusion**: No changes to conversion infrastructure are required during the scaffold or
implement phases. The `zz_generated.conversion_spokes.go` files and the kustomize webhook patch
can be left completely untouched during parallel operation.

## Kustomize Webhook Patch: Global But Harmless During Parallel Phase

`package/kustomize/kustomization.yaml` applies a patch to **every** CRD:

```yaml
patches:
- path: webhook.yaml
  target:
    group: apiextensions.k8s.io
    kind: CustomResourceDefinition
```

`package/kustomize/webhook.yaml` sets `strategy: Webhook` and `path: /convert` on all CRDs:

```yaml
spec:
  conversion:
    strategy: Webhook
    webhook:
      clientConfig:
        service:
          path: /convert
      conversionReviewVersions:
      - v1
```

This means:
1. **Every CRD** (including native RAW CRDs once deployed) will have `strategy: Webhook`.
2. However, the Kubernetes API server only **calls** the conversion webhook when a request
   arrives for a version that is NOT the stored version, AND the CRD serves multiple versions.
3. For single-version CRDs (all RAW types during parallel phase), the webhook strategy setting
   is irrelevant — no conversion is ever requested.

**At cutover**, when the native type replaces the TF type and potentially serves multiple API
versions (see [crd-versioning-strategy.md](crd-versioning-strategy.md)), the webhook WILL be
called. The `ConvertTo`/`ConvertFrom` methods in the old spoke packages must be safe by that time.

**No changes needed to `package/kustomize/kustomization.yaml`** — the global patch is fine for
both single-version native CRDs and multi-version CRDs that have proper conversion handlers.

## At Cutover: Remediation for Multi-Version Resources

At cutover, the native type becomes the hub for its CRD. Any existing objects stored under old
(spoke) versions must be converted through the hub. The spoke packages still contain
`zz_generated.conversion_spokes.go` with `resource.Terraformed` casts — these **must be fixed
before or during cutover**.

### Option A (Recommended): JSON Round-Trip Replacement

Replace `ujconversion.RoundTrip(dstRaw.(resource.Terraformed), tr)` with a plain
`encoding/json` round-trip. This works because `ujconversion.RoundTrip` itself is implemented
as a JSON marshal/unmarshal cycle — the `resource.Terraformed` requirement is only for the
function signature, not for any semantic reason.

**Implementation**: For each spoke version of an affected resource, create a hand-written
conversion file that shadows or replaces the generated spokes:

```go
// apis/cluster/rds/v1beta1/conversion_instance.go
// Hand-written replacement for the zz_generated.conversion_spokes.go entry.
// DO NOT delete zz_generated.conversion_spokes.go — instead, remove just the Instance
// methods from it by adding a build tag exclusion or splitting the file.

package v1beta1

import (
    "encoding/json"

    rdsv1beta3 "github.com/upbound/provider-aws/apis/cluster/rds/v1beta3"
    "github.com/pkg/errors"
    "sigs.k8s.io/controller-runtime/pkg/conversion"
)

// ConvertTo converts this Instance to the hub type (v1beta3).
func (tr *Instance) ConvertTo(dstRaw conversion.Hub) error {
    dst, ok := dstRaw.(*rdsv1beta3.Instance)
    if !ok {
        return errors.Errorf("unexpected hub type %T", dstRaw)
    }
    data, err := json.Marshal(tr)
    if err != nil {
        return errors.Wrap(err, "cannot marshal spoke Instance to JSON")
    }
    if err := json.Unmarshal(data, dst); err != nil {
        return errors.Wrap(err, "cannot unmarshal spoke Instance JSON into hub")
    }
    return nil
}

// ConvertFrom converts from the hub type (v1beta3) to this Instance.
func (tr *Instance) ConvertFrom(srcRaw conversion.Hub) error {
    src, ok := srcRaw.(*rdsv1beta3.Instance)
    if !ok {
        return errors.Errorf("unexpected hub type %T", srcRaw)
    }
    data, err := json.Marshal(src)
    if err != nil {
        return errors.Wrap(err, "cannot marshal hub Instance to JSON")
    }
    if err := json.Unmarshal(data, tr); err != nil {
        return errors.Wrap(err, "cannot unmarshal hub Instance JSON into spoke")
    }
    return nil
}
```

> **Important**: Because `zz_generated.conversion_spokes.go` is generated and cannot be
> edited directly (it would be overwritten by `make generate`), the cutover ticket must also
> ensure `make generate` is NOT run for the TF type after the handwritten conversion file is
> added. By cutover, the TF types and their generated files are being deleted anyway.

### Option B: In-Place Object Migration Before Cutover

Before setting the native type as the new hub, run a one-time migration job that:
1. Lists all objects stored under the OLD spoke version in etcd.
2. Re-saves each object under the new native storage version (using `kubectl apply` or a
   migration controller).
3. Once all objects are migrated, drop the old spoke version from the CRD's `spec.versions`.

After migration, the old spoke `ConvertTo`/`ConvertFrom` methods are never called — they can
safely remain with the broken `resource.Terraformed` cast.

**Drawback**: This approach requires careful coordination and a working migration job before
the CRD cutover can be done atomically. Option A is simpler and safer.

### Kustomize Patch at Cutover

No changes to `package/kustomize/kustomization.yaml` are needed at cutover either. The global
`strategy: Webhook` patch remains correct. The conversion webhook server (deployed alongside
the provider) handles all versions; it will route conversion requests to the `ConvertTo`/`ConvertFrom`
methods registered by the native hub type.

## Why Single-Version Services Are Safe

118 out of 122 services only have a single API version (`v1beta1`). Each type in those services:
1. Implements `Hub()` (from `zz_generated.conversion_hubs.go`) — it IS the hub.
2. Also has `ConvertTo`/`ConvertFrom` (from `zz_generated.conversion_spokes.go`) — but these
   methods are **never called** by Kubernetes because there is no other version to convert from/to.

The `resource.Terraformed` cast in these never-called methods is dead code during the parallel
phase AND at cutover for single-version resources. **No changes are required for these 118 services.**

---

## Cutover Ticket Requirements for Affected Services

For each of the 4 at-risk services (autoscaling, connect, kafka, rds), the cutover ticket MUST:

1. **Identify affected spoke files**: From the tables above.

2. **Write hand-crafted conversion functions** that replace the generated ones. Use Option A
   (JSON round-trip) unless field-level semantic differences require custom logic.

3. **Remove or replace the generated functions**: Since `zz_generated.conversion_spokes.go`
   cannot be edited directly (generated), the cutover must:
   - Delete the affected `zz_generated.conversion_spokes.go` file(s) and replace with a
     hand-written `conversion_spokes.go` (without `zz_` prefix), OR
   - Since TF type files are ALL being deleted at cutover anyway, simply deleting the
     spoke-version package after in-place migration (Option B) is also valid.

4. **Verify conversion works end-to-end**:
   ```bash
   # Example: verify rds.Instance v1beta1 → v1beta3 conversion
   kubectl get instance.rds.aws.upbound.io -o yaml --as-version v1beta1
   kubectl get instance.rds.aws.upbound.io -o yaml --as-version v1beta3
   ```

5. **Reference this document** in the cutover ticket description.

## Summary

| Phase | Conversion Risk | Action Required |
|-------|----------------|-----------------|
| Parallel (RAW types, single-version) | None | None |
| Parallel (TF types still serving multi-version) | None (TF hub still implements Terraformed) | None |
| Cutover (native hub replaces TF hub, multi-version) | **HIGH** for 4 services | Rewrite spoke conversion methods (JSON round-trip) |
| Post-cutover (single-version resources) | None | None |

**Bottom line**: The only conversion panic risk is at cutover for resources in `autoscaling`,
`connect`, `kafka`, and `rds` where multiple API versions are served. All other resources
(118 services) are safe throughout the migration. The kustomize webhook patch requires no
changes at any phase.
